DevOne Apps

Build full applications that run alongside DevOne Core

DevOne Apps are installable application packages for features that are larger than a normal plugin. An App can include its own routes, views, storage, Composer dependencies, framework runtime, and business logic while DevOne Core continues to provide the CMS, authentication, permissions, marketplace, package security, and multisite foundation.

Apps, plugins, and modules

Plugin

Extends DevOne directly through hooks, filters, admin pages, and Core Services.

Module

Adds trusted application features that are loaded as part of the DevOne runtime.

App

Runs as a mounted application with its own entry file, storage area, routes, and optional isolated Composer autoloader.

Theme

Controls presentation, templates, styles, and front-end assets for a DevOne site.

Required package structure

customer-portal/
├── app.json
├── public/
│   └── index.php
├── src/
├── views/
├── assets/
├── vendor/                 optional bundled Composer packages
├── composer.json           optional developer metadata
├── composer.lock           recommended when Composer is used
└── README.md

The ZIP must contain one top-level App folder. The folder must include app.json and the entry file declared by the manifest.

App manifest

{
  "name": "Customer Portal",
  "slug": "customer-portal",
  "version": "1.0.0",
  "description": "A customer account and support portal.",
  "author": "Your Company",
  "type": "devone-app",
  "mount": "/portal",
  "entry": "public/index.php",
  "capabilities": [
    "auth.read",
    "content.read",
    "media.write"
  ],
  "requires": {
    "php": "8.1",
    "devone": "1.3.0"
  }
}

slug must be unique, mount is the URL path assigned to the App, and entry is resolved inside the App folder. Never use an absolute path or a path containing ...

App entry file

<?php

declare(strict_types=1);

// DevOne prepares this context before dispatching the App.
$app = $devone_app;

$currentUser = $app['core']->service('auth')->currentUser();
$storagePath = $app['storage'];
$requestedPath = $app['path'];

header('Content-Type: text/html; charset=utf-8');
?>
<h1>Customer Portal</h1>
<p>Welcome, <?= htmlspecialchars($currentUser['name'] ?? 'Guest') ?></p>

Runtime context

$devone_app['root'];       // Absolute App package directory
$devone_app['storage'];    // Writable storage assigned to this App and site
$devone_app['manifest'];   // Parsed app.json values
$devone_app['mount'];      // Registered URL mount
$devone_app['path'];       // Request path inside the mount
$devone_app['core'];       // DevOne Core Services bridge

Apps should use the supplied Core Services bridge instead of connecting directly to DevOne internal tables. This keeps Apps compatible with single-site, multisite, Pro, Enterprise, and future Core releases.

Composer and framework packages

An App may bundle a framework such as Laravel, Symfony, Slim, or a custom Composer application. Build dependencies before publishing and include the resulting vendor/ directory for one-click installations on hosts without shell access.

composer install --no-dev --prefer-dist --optimize-autoloader

Each App keeps its own vendor/autoload.php. Do not copy App dependencies into DevOne Core and do not assume that another App provides a package.

Installation and routing

  1. The administrator installs the ZIP or supplies an approved HTTPS/CDN package URL.
  2. DevOne validates the archive, manifest, paths, checksum, and package integrity.
  3. The package is extracted into the Apps directory and registered for the current site or network scope.
  4. DevOne creates an isolated writable storage directory.
  5. The administrator reviews requested capabilities and activates the App.
  6. Requests matching the App mount are dispatched to its declared entry file.

Multisite behavior

In a multisite installation, one physical App package may be assigned to multiple sites without duplicating its source files. Activation, settings, storage, permissions, and route ownership remain site-scoped. Network Apps may be made available across the network by an authorized Pro, Enterprise, or SuperAdmin owner.

Packaging checklist

  • Use one top-level folder whose name matches the App slug.
  • Include a valid app.json and a real entry file.
  • Lock dependency versions and bundle production dependencies when marketplace users may not have Composer.
  • Write only to the supplied App storage directory.
  • Request only the capabilities the App actually needs.
  • Do not modify DevOne Core, another package, or another site's files.
  • Include version, author, license, support, upgrade, and uninstall information.
  • Test installation, activation, routing, update, deactivation, and uninstall before submission.

Marketplace and CDN delivery

Marketplace Apps may be delivered from the DevOne package CDN. The CDN only distributes the signed package; DevOne still performs license checks, checksum verification, scanning, extraction, registration, health checks, and rollback. Published packages should use exact versions and immutable release archives.

Security requirements

Apps execute PHP and must be treated as trusted application code. DevOne and Guardian can inspect packages, but developers remain responsible for secure coding, dependency maintenance, authorization checks, input validation, output escaping, and safe database usage.
